1 OVERVIEW / ພາບ ລວມ

1.1 Purpose/ ຈຸດປະສົງ

ລະບຽບ ນີ້ ອະທິບາຍ ຂັ້ນຕອນ ການ ພັດທະນາ, ທົດສອບ, ຮັບປະກັນ ຄວາມ ປອດໄພ, ຕິດຕັ້ງ ແລະ ຄຸ້ມຄອງ ການ ປ່ຽນແປງ ຂອງ ລະບົບ ຄຸ້ມຄອງ ສາງ (WH) — ເພື່ອ ໃຫ້ ໝັ້ນ ໃຈ ວ່າ ລະບົບ ຖືກ ສ້າງ ຂຶ້ນ ຢ່າງ ມີ ມາດຕະຖານ, ກວດສອບ ໄດ້ ແລະ ປອດໄພ ກ່ອນ ນຳ ໃຊ້ ຕົວ ຈິງ ທົ່ວ ອົງກອນ.

This procedure describes how the WH application is developed, tested, secured, deployed and change-managed, ensuring it is built to a controlled, auditable and secure standard before organisation-wide use.

1.2 Scope/ ຂອບເຂດ

ໃຊ້ ກັບ ຕົວ ແອັບ WH (Laravel 12 + Livewire), repository ໂຄ້ດ, ສະພາບ ແວດ ລ້ອມ ທັງ ໝົດ (ພັດທະນາ / UAT / ຕົວ ຈິງ) ແລະ ທຸກ ຝ່າຍ ທີ່ ກ່ຽວຂ້ອງ ກັບ ການ ພັດທະນາ, ທົດສອບ, ຕິດຕັ້ງ ແລະ ບຳລຸງ ຮັກສາ ລະບົບ.

Applies to the WH application, its source repository, all environments (development / UAT / production), and everyone involved in developing, testing, deploying and maintaining it.

1.3 Maintenance/ ການ ບຳລຸງ ຮັກສາ

ເອກະສານ ນີ້ ຄຸ້ມຄອງ ໂດຍ Warehouse Information Division, ທົບທວນ ຢ່າງ ໜ້ອຍ ປີ ລະ ຄັ້ງ ຫຼື ເມື່ອ ລະບົບ ມີ ການ ປ່ຽນແປງ ໃຫຍ່. ການ ບຳລຸງ ຮັກສາ ລະບົບ ລວມ ມີ:

  • ອັບເດດ dependency + ກວດ ຊ່ອງ ໂຫວ່ — composer audit ເປັນ ປົກກະຕິ; ປັບປຸງ ຊຸດ ໂປຣແກຣມ ທີ່ ມີ CVE.
  • Backup ຖານ ຂໍ້ມູນ — backup ກ່ອນ ທຸກ ການ ປ່ຽນແປງ + ຕາມ ຮອບ; ມີ ໜ້າ Backup/Restore ໃນ ລະບົບ.
  • ຕິດຕາມ log + ແກ້ໄຂ — ເຝົ້າ ລະວັງ error log ແລະ Audit Log; ແກ້ໄຂ ບັນຫາ ຕາມ ຂັ້ນຕອນ ຄວບຄຸມ ການ ປ່ຽນແປງ (ຂໍ້ 2.6).

Owned by the Warehouse Information Division; reviewed at least yearly or on major change. System maintenance covers dependency updates + vulnerability scanning, regular backups, and log/audit monitoring with controlled remediation.

2 PROCEDURE / ຂັ້ນຕອນ ປະຕິບັດ

2.1 Business Requirement Definition/ ກຳນົດ ຄວາມ ຕ້ອງການ

2.1.1 Purpose / ຈຸດປະສົງ

ເກັບ ກຳ ແລະ ບັນທຶກ ຄວາມ ຕ້ອງການ ທຸລະກິດ ຂອງ ວຽກ ສາງ ໃຫ້ ຄົບ ຖ້ວນ, ເພື່ອ ໃຫ້ ການ ພັດທະນາ ຢູ່ ຕົງ ຕາມ ຄວາມ ຕ້ອງການ ຈິງ.

Capture and document the warehouse business needs the system must meet, so development targets real requirements.

2.1.2 Workflow / ຂັ້ນຕອນ

ເກັບ ຄວາມ ຕ້ອງການ→ວິເຄາະ + ຈັດ ໝວດ ໂມດູລ→ຂຽນ ເອກະສານ→ຢືນຢັນ ກັບ ຜູ້ ໃຊ້/ຫົວໜ້າ

2.1.3 Details / ລາຍລະອຽດ

  • ທົດແທນ ລະບົບ ເກົ່າ WIBT (Firebase) ດ້ວຍ ລະບົບ ໃໝ່ ທີ່ ຄຸ້ມຄອງ ຄົບ ວົງຈອນ ສາງ ແລະ ຮອງຮັບ ພາສາ ລາວ ເຕັມ ຮູບແບບ.
  • ຂອບເຂດ ໂມດູລ: ສາງ ວັດສະດຸ, ຢືມ, ຝາກ, ເບີກ, ເຄື່ອງມື+ບຳລຸງຮັກສາ, ກວດ ສະຖານທີ່, ຈຳໜ່າຍ, DA/OGA, ບັນຊີ ສິນຄ້າ, ງານ ວາງສະແດງ, ບໍລິຫານ ລະບົບ.
  • ຂໍ້ ກຳນົດ ຫຼັກ: ຄວບຄຸມ ສິດ ຕາມ ບົດບາດ (RBAC 24 ເມນູ), soft-delete + ເຫດຜົນ, ໃບ PDF ຫົວ ທາງ ການ SCU-WID, Audit Log ບັນທຶກ ທຸກ ການ ກະທຳ.
  • ຍ້າຍ ຂໍ້ມູນ: ຂໍ້ມູນ ການ ຢືມ ທີ່ ໃຊ້ ຢູ່ ຈິງ ໃນ ລະບົບ ເກົ່າ ຕ້ອງ ຍ້າຍ ເຂົ້າ ລະບົບ ໃໝ່ ໂດຍ ຮັກສາ ຄົບ.

2.2 Solution Design and Development/ ອອກແບບ ແລະ ພັດທະນາ

2.2.1 Purpose / ຈຸດປະສົງ

ອອກແບບ ໂຄງສ້າງ ທີ່ ໝັ້ນຄົງ, ປອດໄພ ແລະ ບຳລຸງ ຮັກສາ ໄດ້ ງ່າຍ, ແລ້ວ ພັດທະນາ ໂມດູລ ໃຫ້ ຕົງ ຕາມ ຂໍ້ ກຳນົດ.

Design a maintainable, secure architecture and build the modules to specification.

2.2.2 Workflow / ຂັ້ນຕອນ

ອອກແບບ schema + UI→ພັດທະນາ ໂມດູລ→ຂຽນ test (Pest)→review + ປັບປຸງ→commit

2.2.3 Details / ລາຍລະອຽດ

  • ເຕັກໂນໂລຢີ: Laravel 12 · Livewire 3 / Volt · MySQL · Pest (ຊຸດ ທົດສອບ ອັດຕະໂນມັດ) · spatie/permission (RBAC).
  • ມາດຕະຖານ ດຽວ ກັນ: ໜ້າ ຕາ ຮ່ວມ (app-header + sticky), ຟອມ validation ພາສາ ລາວ (ແຈ້ງ ເຕືອນ ສີ ເຫຼືອງ), ລະບົບ ແປ/ແທນ ຄຳ ທົ່ວ ແອັບ.
  • ຄວບຄຸມ ຂໍ້ມູນ: soft-delete + ເຫດຜົນ + Deleted Log + restore ທົ່ວ ລະບົບ; ຮູບແບບ checklist + ຫຼັກຖານ (ຮູບ/ຄລິບ); ໃບ PDF ຫົວ SCU-WID + ລາຍເຊັນ.
  • ຄວາມ ລັບ: ໂຄ້ດ ຢູ່ GitHub (private); ໄຟລ໌ ຄວາມ ລັບ (.env, APP_KEY) ບໍ່ ຖືກ commit.

2.3 User Acceptance Testing (UAT)/ ທົດສອບ ຮັບຮອງ ໂດຍ ຜູ້ ໃຊ້

2.3.1 Purpose / ຈຸດປະສົງ

ຢືນຢັນ ວ່າ ແຕ່ ລະ ໂມດູລ ໃຊ້ ໄດ້ ຕົງ ຕາມ ຄວາມ ຄາດ ຫວັງ ຂອງ ທຸລະກິດ ກ່ອນ ນຳ ໃຊ້ ຕົວ ຈິງ.

Confirm each module meets business expectations before go-live.

2.3.2 Workflow / ຂັ້ນຕອນ

ຕິດຕັ້ງ ໃສ່ UAT→ຜູ້ ໃຊ້ ທົດສອບ ຕົວ ຈິງ→ບັນທຶກ ບັນຫາ→ແກ້ໄຂ→ທົດສອບ ຄືນ→ຮັບຮອງ

2.3.3 Details / ລາຍລະອຽດ

  • ສະພາບ ແວດ ລ້ອມ UAT: wh.homesang.pro (Hostinger VPS · Ubuntu 24.04 · nginx + PHP 8.3 + MySQL · SSL).
  • ຍ່າງ ຜ່ານ ຕົວ ຈິງ: ທົດສອບ login ແລະ ຍ່າງ ຜ່ານ ທຸກ ໂມດູລ (13/13) ຜ່ານ ຄົບ.
  • ທົດສອບ ຫຼາຍ ຄົນ: ໃຫ້ ເພື່ອນ ຮ່ວມ ງານ ທົດສອບ ຈາກ ເຄື່ອງ/ໂທລະສັບ ອື່ນ ຜ່ານ cloudflared tunnel.
  • ທົດສອບ ອັດຕະໂນມັດ: ຊຸດ Pest 422 ກໍລະນີ ຜ່ານ ໝົດ (regression ກ່ອນ ທຸກ ຄັ້ງ ທີ່ deploy).

2.4 System Penetration Testing/ ທົດສອບ ຄວາມ ປອດໄພ

2.4.1 Purpose / ຈຸດປະສົງ

ຄົ້ນ ຫາ ແລະ ແກ້ໄຂ ຊ່ອງ ໂຫວ່ ດ້ານ ຄວາມ ປອດໄພ ກ່ອນ ຂຶ້ນ ຕົວ ຈິງ — ປົກ ປ້ອງ ຂໍ້ມູນ ແລະ ການ ເຂົ້າ ເຖິງ.

Find and remediate security vulnerabilities before production; protect data and access.

2.4.2 Workflow / ຂັ້ນຕອນ

ກວດ static + dynamic→ບັນທຶກ ຊ່ອງ ໂຫວ່→ແກ້ໄຂ→ກວດ ຄືນ→ຢືນຢັນ ສະອາດ

2.4.3 Details / ລາຍລະອຽດ

  • ຄວບຄຸມ ສິດ + IDOR: RBAC ຄົບ ທຸກ ເມນູ; ແກ້ ໃຫ້ ຜູ້ ໃຊ້ ເຂົ້າ ໄດ້ ສະເພາະ ຂອບເຂດ ຕົນ (ເຄື່ອງມື / ຈຳໜ່າຍ / DA-OGA ຕາມ ພະແນກ ຫຼື ເຈົ້າ ຂອງ).
  • Auth / session: ລະຫັດ ເຂົ້າ ລະຫັດ (bcrypt) · ບັງຄັບ HTTPS · cookie ປອດໄພ · ຈຳກັດ ຄວາມ ພະຍາຍາມ login · ຕັດ session ບັນຊີ ທີ່ ຖືກ ປິດ · ບັງຄັບ ປ່ຽນ ລະຫັດ ຄັ້ງ ທຳ ອິດ.
  • Input / file: ແກ້ path-traversal ຕອນ ນຳ ເຂົ້າ ຮູບ (ຢືນຢັນ ເສັ້ນທາງ) · ຊື່ ໄຟລ໌ ຮູບ ສຸ່ມ ປອດໄພ (CSPRNG) · ຈຳກັດ ປະເພດ ໄຟລ໌ upload.
  • Concurrency: ລັອກ ແຖວ (lockForUpdate) ຕອນ ຮັບ ຄືນ ຢືມ ແລະ ອອກ ເລກ ໃບ · ໃຊ້ DB transaction · unique index ກັນ ເລກ ຊ້ຳ.
  • Dependencies: ອັບເດດ ຊຸດ ທີ່ ມີ CVE (dompdf, guzzle, commonmark); composer audit = clean.
  • Prod gates: APP_ENV=production · APP_DEBUG=false · SESSION_SECURE_COOKIE=true · TRUSTED_PROXIES ≠ '*'.
  • ການ ສະແດງ ຜົນ + algorithm: ກວດ ການ ອອກ ຂໍ້ມູນ ແລະ ຂັ້ນຕອນ ຄິດໄລ່ ທັງ ໝົດ = ສະອາດ (escape ຄົບ, ບໍ່ ຮົ່ວ ຂໍ້ມູນ ຂ້າມ ຂອບເຂດ).
  • Live host: TLS / security headers / cookies ໃນ ໂຮສ ຈິງ ກວດ ຜ່ານ ສະອາດ.

2.5 Deployment & Verification/ ຕິດຕັ້ງ ແລະ ກວດ ຢືນຢັນ

2.5.1 Purpose / ຈຸດປະສົງ

ຕິດຕັ້ງ ເວີຊັນ ທີ່ ທົດສອບ ແລ້ວ ໃສ່ ໂຮສ ເປົ້າ ໝາຍ ຢ່າງ ໝັ້ນຄົງ ແລະ ກວດ ຢືນຢັນ ກ່ອນ ໃຊ້ ງານ.

Deploy the tested build to the target host reliably and verify it before use.

2.5.2 Workflow / ຂັ້ນຕອນ

ແພັກ + backup→ຕິດຕັ້ງ (composer/.env/migrate/seed)→storage + cache→restart service→ກວດ ຢືນຢັນ

2.5.3 Details / ລາຍລະອຽດ

  • ຂັ້ນຕອນ ຕິດຕັ້ງ: composer install --no-dev · ຄັດລອກ .env + key:generate · migrate --force · seed (RBAC, super_admin, ແມ່ແບບ) · storage:link · config/route/view cache · ຕັ້ງ ສິດ storage + bootstrap/cache.
  • ຍ້າຍ ຂໍ້ມູນ ຢືມ: borrow:import-json --refresh + import-photos (78 ໃບ, 142 ຮູບ) — ອ່ານ ຈາກ ແຫຼ່ງ ເກົ່າ ແບບ read-only ເທົ່ານັ້ນ.
  • ກວດ ຫຼັງ ຕິດຕັ້ງ: ນັບ ໃບ ຢືມ = 78 (returned 58 / active 20) · login super_admin · ຍ່າງ ຜ່ານ ເມນູ.
  • ໂຄງສ້າງ server: wh.homesang.pro (UAT/ໃຊ້ ປັດຈຸບັນ) → wh.namtheun2.com (ຕົວ ຈິງ, cutover). ຕ້ອງ restart php8.3-fpm ຫຼັງ deploy (ລ້າງ OPcache).
🔐 ກ່ອນ go-live ຕ້ອງ ຢືນຢັນ: APP_DEBUG=false · SESSION_SECURE_COOKIE=true · TRUSTED_PROXIES = IP edge ຈິງ · APP_KEY + SUPER_ADMIN_PASSWORD ຕັ້ງ ແລ້ວ · SMTP ຈິງ (ບໍ່ ດັ່ງນັ້ນ ລິ້ງ ຕັ້ງ ລະຫັດ ຈະ ຂຽນ ລົງ log).

2.6 Version Control & Change Management/ ຄວບຄຸມ ເວີຊັນ ແລະ ການ ປ່ຽນແປງ

2.6.1 Access Control to Source Code / ຄວບຄຸມ ການ ເຂົ້າ ເຖິງ ໂຄ້ດ

  • ໂຄ້ດ ຢູ່ GitHub (private repo sonehomesang/WIS); ໃຫ້ ສິດ ສະເພາະ ຜູ້ ກ່ຽວຂ້ອງ.
  • ຄວາມ ລັບ (.env, APP_KEY, ລະຫັດ DB, service account) ບໍ່ commit — ຢູ່ ໃນ .gitignore, ຕັ້ງ ໃນ server ໂດຍ ກົງ.

2.6.2 Software Version Control / ຄວບຄຸມ ເວີຊັນ

  • ໃຊ້ Git, branch ຫຼັກ main; commit ມີ ຂໍ້ຄວາມ ຊັດເຈນ (feat/fix/docs + scope); ປະຫວັດ ຄົບ ກວດສອບ ໄດ້.
  • deploy ຜ່ານ git pull (assets ມາ ພ້ອມ); ສາມາດ ຍ້ອນ (rollback) ຄືນ commit ເກົ່າ ໄດ້.

2.6.3 Change Management / ຄຸ້ມຄອງ ການ ປ່ຽນແປງ

  • ທຸກ ການ ປ່ຽນແປງ: ທົດສອບ ໃນ dev → commit → deploy ໃສ່ UAT → ຢືນຢັນ → ຈຶ່ງ ຂຶ້ນ prod.
  • Backup ຖານ ຂໍ້ມູນ (mysqldump) ກ່ອນ ປ່ຽນ; ໃຊ້ migration ຄຸ້ມຄອງ schema; restart service ຫຼັງ deploy.
  • Audit Log ບັນທຶກ ການ ກະທຳ ໃນ ລະບົບ; ໜ້າ Backup/Restore ຢູ່ ໃນ ເມນູ ບໍລິຫານ.

2.6.4 External Vendors / ຜູ້ ໃຫ້ ບໍລິການ ພາຍ ນອກ

  • ໄອທີ / vendor ຮັບຜິດຊອບ ຕິດຕັ້ງ ຢູ່ wh.namtheun2.com ຕາມ ຊຸດ cutover ທີ່ ມອບ ໃຫ້ (ໂຄ້ດ + ຂໍ້ມູນ + runbook).
  • ການ ເຂົ້າ ເຖິງ ຂໍ້ມູນ ຕົວ ຈິງ ຂອງ ລະບົບ ເກົ່າ (WIBT / Firebase) ເປັນ read-only ເທົ່ານັ້ນ.
  • ບໍລິການ ພາຍ ນອກ ອື່ນ: Google Cloud / Firebase (ລະບົບ ເກົ່າ, ໃຊ້ ຍ້າຍ ຂໍ້ມູນ), SMTP mail, VPS host — ຄວບຄຸມ ສິດ + ຄວາມ ລັບ ຕາມ ຂໍ້ 2.6.1.
